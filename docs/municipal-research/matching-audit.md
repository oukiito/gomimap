# 住宅設定と収集区分の瑕疵点検

2026-10-10／[Issue #73](https://github.com/oukiito/gomimap/issues/73)。設計上の欠落と対策を記録する。全国全行を検証して「瑕疵なし」と判定した記録ではない。現行アプリは架空地区のschema1で、以下は製品v2へ反映する設計。実装開始には自治体別MR01〜09と設計レビューが必要。

## 発見した問題

| ID | そのまま実装すると起きる誤り | 根拠／修正 |
| --- | --- | --- |
| MA01 | GPSや町丁目の一致だけで全品目を確定する | [横浜](yokohama.md)の除外・範囲、[豊島](toshima.md)の号・道路。条件が不明なら候補のまま。三値と明示的な例外関係を維持 |
| MA02 | 自宅から最寄りの集積所を選ぶ | [名古屋](nagoya.md)の利用対象別。判定に使う事実が住宅住所か集積所所属かを分け、後者は利用対象の根拠確認が必要 |
| MA03 | 番号が同じなら同じ予定になる | [大阪](osaka.md)の建物別。建物・収集主体の確認が必要な範囲をcoverageに含める。建物の判定を省いて「住所対応済み」としない |
| MA04 | 資源のまとめ欄を永久に一つの周期とする | [名古屋](nagoya.md)モデル事業。category・方式・期間で分割可能にし、地域限定の適用関係を確認 |
| MA05 | 収集時間帯の終了を排出締切とする | [大阪](osaka.md)。排出の規則と車両到着の目安を別型にする。時刻経過で収集済みと断定しない |
| MA06 | 時間だけ不明でも日付・品目まで消す | [大阪](osaka.md)の時間要照会。所属・日付・排出時刻の確定状態を別々に持つ |
| MA07 | 市収集欄の空白を収集なしとする | 大阪のコミュニティ回収、横浜・豊島の集団回収。空欄の意味を資料ごとに確認。別方式へ分岐しても、その日程が分かるとは限らない |
| MA08 | 電池なら全国一律に回収地図へ送る | 横浜の備考・名古屋の品目欄には家庭からの収集がある。品名と回収方式を分け、自治体で可能な方法を案内。地図は公共持込拠点用のまま |
| MA09 | 粗大ごみの定例日を、その人が出せる日として通知する | 名古屋の事前申込制。申込先案内と予約済み予定は別。現段階は予約登録・代行を実装しない |
| MA10 | 都市部の一般住所で成立すれば全国対応可能とする | 札幌の条・番号、福岡の夜間、京都の民間収集。町村・島しょ・広域組合・自治会所属の反例も必要。人口順位を理由に未調査方式を対応済みにしない |

## 判定契約の補強（設計、未実装）

### 所属と対応能力

AssignmentRuleに`basis`を持たせる候補：`residenceAddress`、`authorizedStationMembership`、`buildingService`、`officialCalendarSelection`、`communityMembership`。一つのルールで複数必要ならANDの条件として明示する。GPSの幾何一致を所属の証明へ変換しない。

coverageは自治体名だけでなく **実施主体×方式×品目×条件×有効期間** に対して、扱える／追加情報で解ける／公式確認が必要／未対応を持つ。建物例外を除外した住所域を全域対応としない。民間収集か不明なら市収集を既定にしない。本人が「違う」「分からない」を選べることと、未検証の自由入力で公式ルールを作れることを混同しない。

本人確認は位置と所属の取り違いを減らす最後の確認で、元資料の誤りを補償する検証ではない。住所を変えたら依存する集積所・建物・団体の回答を破棄する。共通の住所回答は一度だけ聞き、方式ごとの全入力を繰り返させない。

### 日付・時間・通知

bindingの所属状態に加えて、予定に`dateStatus`と`timeStatus`を持つ。例えば所属と曜日が確認済み、時間が要照会という組合せを許容する。日付が不明な「収集予定の確認が必要」と、日付は確定しているが「出す時間を公式情報で確認」を混同しない。

時間の候補型は次の四つ。完全なJSON／codecは未確定で、名前だけをschema1へ追加しない。

| 種類 | 意味 | 自動動作 |
| --- | --- | --- |
| `putOutDeadline`／`putOutWindow` | 公式に根拠のある排出期限・許容時間。持ち出し日からdayOffset付き | 検証済みの終了で次回へ切替可能。表示は「排出期限経過」で、収集完了の証明ではない |
| `collectionEstimate` | 車両が来るおおよその時間 | 始端も終端も、自動で厳密な排出期限へ変換しない |
| `relativeGuidance` | 目安時間帯前・日没後などの原文に基づく案内 | 未検証の固定時刻を作らず、人が読める説明を保持 |
| `unknown` | 出す時間を確定できない | 朝10時等の推測による自動繰越なし |

終了が未確定の方式は当日の予定を日付が変わるまで保持し、次の予定を補助表示する。これは「まだ出してよい」の意味ではない。日付変更時は前日の確認事項を当日の未知予定として持ち越さず、前日詳細で参照できる。日跨ぎの許容窓がある場合はdayOffset付きの公式終了を優先する。不明な日程自体は従来どおり飛ばさない。

現行の「終了前に届ける通知」の製品契約では終了未確定を予約しない。日時が判明しているだけの事前予定通知を追加する場合は別モードの文言・遅配・取消を設計してから実装する。この調査で未知の時間帯へ通知を有効化しない。さいたまの早朝地区では朝6時が期限後になり得るため、通知候補は期限より前かを必ず検査する。

### 規則の解釈

住所表の同一列でも品目例外・脚注・リンク先があれば別ルールとして保持する。sourceの更新日、制度施行日、カレンダー対象期間、取得日を分離する。第1・3曜日を14日周期へ置き換えない。「以外」は該当範囲と否定条件が判明した時だけ真。列挙区間の隙間を補間せず、号なしの住所と号未回答を区別する。

## UI・UXの追加理由

全て既存の初回／変更フローに必要時だけ追加する案。常時説明や宣伝の追加ではない。全言語・文字拡大・読み上げ・48pxの実画面検証は未実施。

| ID | 要素・遷移／利用場面と理由 | 戻る・保持・失敗・確認方法 |
| --- | --- | --- |
| NC06／S02 | 資源の利用場所・団体が必要な地域だけ、根拠のある候補と「分からない」、公式確認へ。引越し直後に利用場所を知らなくても他のごみを設定できる | 不明は該当bindingだけ保留。戻ると入力中回答を保持、上位住所を変更したら依存回答を解除。公式ページから戻っても自動確定しない。MA02・07で確認 |
| NC07／S02 | 建物・収集主体の例外がある範囲だけ所属確認。GPSの住所一致で別事業者の予定を案内しない | 非該当と不明は別。候補名が見つからなければ公式・管理者への確認方法を示す。アプリから問い合わせを自動送信しない。取消・失敗時は旧profile維持。MA03で確認 |
| NC08／S04・W | 日付が確定し時間だけ不明なら、日付・品目を保持して時間の確認導線。朝の利用者に判明している情報を失わせない | 公式から戻っただけで状態変更しない。本体とウィジェットで同じ確定状態。翌日への切替・未知時間・読み上げは下のA05〜07で確認 |
| NC09／S08 | 品物ごとに家庭収集／公共持込／予約案内を分ける。電池等を必要なく遠くの拠点へ持参させない | 家庭収集は通常の予定へ、公共持込は地図へ、粗大は公式申込案内へ。戻れば品物と条件を保持し、地区変更時は再判定。MA08・09で確認 |

精密な家・建物・所属IDは端末内の私有データとして扱い、原住所を恒常保存しない。利用地区名の常時表示に部屋番号・建物名を追加しない。保存は旧／新profile全体で一回確定し、部分的に新しい通知だけ出る状態を作らない。

## 残る難所

全対象行の網羅・現行版と利用条件・所属確認の実用性・v2 JSONと保存移行・上記のUI投影は未完成。都市部以外では[大島町・嬬恋村・大網白里市と広域処理主体の反例候補](representative-regions.md)を一次確認した。他の町村等は未調査で、実施主体の詳細調査も必要。今回の反例点検を全国全戸の正確性保証へ読み替えない。
