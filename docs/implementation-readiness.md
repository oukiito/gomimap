# 残作業の難易度・実装前の契約

2026-10-10。[Issue #65](https://github.com/oukiito/gomimap/issues/65)、親[#53](https://github.com/oukiito/gomimap/issues/53)。基準はmain `b216dfe`。以下は次の実装で満たす設計で、実装・配信・検証済みの宣言ではない。既存の[残る設計](remaining-design.md)と各詳細設計の追加契約とする。

[全国向けの対応設計](national-collection-matching.md)（#69）で、単一areaId・朝の同日締切を製品の共通前提にできないことを確認した。D1のcalendar、D4の区域参照、D5のselectionは同書の複数binding／持ち出し時間を前提に修正する。Calendar v2とHomeCollectionProfileのcodec・合成試験が済むまで、製品loader／DeviceState／GPS照合の実装ゲートは未完了。

[MR01〜09の自治体別詳細調査](municipality-rollout.md)は、住宅照合・地域設定・新自治体取込とそれに依存する製品型の実装前に必須。人工fixtureの設計だけで着手しない。豊島区も調査中であり、現在のN01〜08は調査／受け入れの計画である。

## 難易度と優先する理由

| 残作業 | 技術的難度 | 不確実性・難しい部分 | 実装前に必要な結論 |
| --- | --- | --- | --- |
| 5 定期更新・監視 | 最も高い | 取得成功と情報の正しさは別。告知の例外・施行日・LLM失敗・審査・公開・監視を連携する | 取得／候補／承認／公開の分離、公開単位、候補の重複排除、監視先・通知先・費用上限 |
| 4 本体とOSの復旧 | 最も高い | 複数ファイルとOSを一括確定できず、終了位置・遅い呼出・古い予約で混在する | 一つの確定状態、世代照合、保存前後の失敗、破損時の確認付き復旧 |
| 1 実データ | 高い・工程への影響最大 | 区域・例外・年度・権利の確認が外部資料に依存する。コードだけでは解消しない | 項目別の根拠・有効期間・許可、保留する影響範囲、原文照合の責任 |
| 2 GPS地区設定 | 高い | 行政界と収集区域は別。概略位置・境界・自宅以外・区域改定を誤確定しやすい | GPSは候補だけ、精度円の交差、手動代替、区域パックと版の照合 |
| 6 Android実機 | 高い・検証負荷が大きい | OS／ランチャー／省電力の差。時計判定と実配送・描画は別 | 通常／省電力／終了／再起動の試験条件、観測時刻、許容遅延と復帰条件 |
| 3 分別・回収場所 | 中〜高 | 寸法だけで決まらず、例外・不明・利用資格・受付が競合する | 三値判定、例外優先、質問の選び方、分類と持込適合・営業の分離 |

これは設計・既存コードに基づく評価で、工数や日程の見積りではない。特に1の未確認資料を増やしても、5の取得が動くだけで実用版にはならない。

## 共通の不変条件

- 不明を収集なし・一般ごみ・粗大ごみ・受入可に変換しない。
- 保存成功前に地区・本体の予定を変えない。確定後のOS失敗で本体を黙って旧状態へ戻さない。
- 日程・分類・区域・拠点は同じ自治体リリースを使う。新しい分類と古い受付条件を混ぜない。
- fixtureと製品は名前空間を分け、実GPS・実住所をサンプルへ対応付けない。
- UIは利用者の次の行動に必要な確認だけ。正常時の追加メッセージ・装飾・全機能の一括案内を増やさない。

## D1 公開・端末保存の単位

現在のschema1は日程・区域・品物・拠点・サービスを含むが、分別分類ルールと地理境界は未定義。schema1へ未知キーを追加せず、次の製品形式は**自治体ごとの一つのReleaseBundle v2**にする。分別と日程を別々に切り替えないためである。

| フィールド | 契約 |
| --- | --- |
| bundleSchemaVersion | 2。未知版を拒否 |
| kind／channel | kindはfixture／verifiedでbundle・calendar・manifest一致。channelはdevelopment／productionでbundle・manifest一致。productionならcalendar.kind=verifiedと出典登録簿の公開検査が必須 |
| municipalityId／releaseId／releaseNumber | 自治体の固定ID・不変版ID・自治体内の単調増加整数。番号は1〜2^53−1。番号の順序を公開日時から推測しない |
| publishedAt／validPeriod | UTC公開日時、日本日付の有効期間。開始を含み終了を含まない |
| calendar | 製品はCalendar v2の別契約。stream・区域・対応規則・日程・coverageを持ち、外側の自治体・版・期間と照合。現在のschema1はfixture用に維持 |
| sorting | SortingRules v1。calendarのitem・category・sourceのIDへ参照 |
| geo | GeoPack v1またはnull。nullならGPSの区域解決を提供しない |
| provenance／approval | 元資料hash・原文位置・条件の確認記録・審査PR／採用commit。文字列があるだけで人の照合を省略しない |

初版のbundleはUTF-8で2MiB以下（圧縮後だけの上限にしない）。超える実資料は勝手に省略・境界簡略化せず、上限・分割方式を別の設計変更として扱う。製品Calendar v2内部の版IDはreleaseIdと一致させ、geo／sortingは必ず同じreleaseIdを参照する。各内部形式も版・参照・期間・根拠を検証する。

manifest v2はbundleの不変HTTPSパス、sha256、bytes、releaseNumber、自治体・kind／channel・採用sourceCommitを指定する。同じreleaseId／番号の異内容を拒否する。番号の比較基準は確定済みの検証済みreleaseであり、取得に失敗した高番号のmanifestだけで更新を確定しない。サーバー側は全体検証→不変bundle配置→manifest切替の順。端末では不変bundleの検証・保存は準備だけで、参照版の変更はD5のDeviceState.selectionの原子的確定のみとする。別の端末current版ポインタを先に書き換えない。更新中の読者はDeviceStateが示す一つの版だけを見る。現在と直前の検証済みbundleを保持するが、欠落・破損した新しい版へ旧版の一部を混ぜない。manifestとbundleが一時的に一致しなければ有効な旧版を保持して再試行する。

誤公開の訂正は番号を進めた新しいリリース。旧内容を採用する場合も新しいreleaseId／番号・審査・訂正理由を付ける。過去の期間を勝手に延ばさず、旧番号への降版拒否を外さない。旧パスは現行・直前版に必要な範囲で配信bundle内へ残す。

`DemoDatasetRepository`とCloudflareのmanifest v1は現在のfixture専用として保持する。製品loaderとDeviceState v2を追加し、サンプルA／Bを実地区へ移行しない。互換性試験で旧fixtureの起動・オフライン・同版差替え拒否を維持する。

## D2 分別判定を先に確定する

SortingRules v1は`version, municipalityId, releaseId, validPeriod, questions, routes, preparations, rules`を必須とする。質問には意味ID・型（bool／enum／有限整数）・単位・測る対象・入力範囲・文言IDを持たせる。ルールにはID・対象item／area・適用期間・明示priority（0〜65535）・AND条件のORグループ・結果・根拠を持たせる。分類ルールと施設のacceptanceRulesを代用し合わない。

結果は`categoryId`／`routeId`（少なくとも片方）と重複なしの順序付き`preparationIds`。categoryIdはcalendar.categories、routeId／preparationIdsはsorting内の登録簿へ参照する。routesは`id, kind, labelMessageId, officialUrl, sourceIds, validPeriod`を必須とし、kindはhousehold／bulkyApplication／recyclingLaw／specialCollection／officialConsultationへ限定。preparationsは`id, messageId, sourceIds, validPeriod`を必須とする。URLは自治体の出典登録で確認した公式HTTPS経路だけで、LLMが返した任意URLを開かない。未知ID・ルールの適用期間を覆わない参照・根拠欠落・全言語に存在しない固定文言IDをbundleの検査で拒否する。対象日がcatalogの期間外なら分類を確定しない。

質問の有限整数はmmの整数精度を意味する。mm入力は整数、cm入力は小数1桁までとし、文字列の十進桁を解析して正確に整数mmへ変換する。30cm／30.0cmは300mm、29.9cmは299mm。29.99cm・299.5mmは丸めず、入力精度の修正を求める。小数点は選択言語の区切りを扱い、桁区切りとの曖昧な値を推測しない。条件はisValue／oneOf／range。新しいrangeにはminInclusive／maxInclusiveを明記する。既存schema1の両端包含を変更せず、cm入力は有限・非負のmmへ正規化する。NaN、無限、単位不明、測っていない値はunknown。

評価順序を固定する。

1. 自治体・地区・対象item・対象日・根拠を照合。現在の版に対象がなければ未対応／確認必要で、区分を補完しない。
2. 各条件をaccepted／rejected／unknownで評価。AND内にrejectedがあればその組はrejected、OR内にacceptedがあればそのルールはaccepted。
3. priorityは大きいほど優先。acceptedの最高順位より上、または同順位のunknownがあれば、低順位の結果を確定しない。acceptedがなければ最高順位unknownから確認する。
4. まず最高順位の未解決グループだけを扱い、欠けている利用者回答は必要な質問を一つずつ出す。そのグループに根拠不明等、質問で解決できないunknownがあれば確認必要へ。上位の質問への回答でacceptedを確立すれば、下位の根拠不明は結論に影響しなくなる。上位がrejectedなら次の順位を再評価する。同順位acceptedのcategory／route／準備IDが異なれば矛盾として保留し、配列順・多数決で決めない。
5. 競合するunknownがなく、最高順位acceptedの結果が同一のときだけ確定。全rejected／該当なしは確認必要で、一般ごみを既定値にしない。

質問は最高順位の未解決条件に限定し、意味IDの固定順で表示する。答えた結果不要になった質問を続けず、住所・写真・自由記述を要求しない。質問の答えは当該用件のメモリだけに保持。品目変更でその品目の答えを解除。版変更では結論を破棄し、質問のID・型・単位が同じ答えだけ再検証する。地区変更では地区依存の答えを解除する。

**自作fixtureの判定例（自治体の実際の基準ではない）**：最大辺300mm以上を粗大、300mm未満を一般とする2ルールなら299／300／301mmで一般／粗大／粗大。より優先する専用処理ルールが未回答なら、301mmでも粗大と断定しない。入力不明は質問または公式確認へ。同順位の一般／粗大競合は確認必要。

## D3 回収地図の契約

`matchServices`の結果を使う。同じfacilityの複数サービスを一つのピンで区別し、サービス名・受付条件・対象者・時刻・根拠を詳細で読めるようにする。通常品目・家庭用集積所は掲載しない。

| 状態 | 地図／一覧・次の行動 |
| --- | --- |
| 未選択 | 特別な品目の公開施設の概観。適合と案内せず経路推薦なし |
| 必須条件未回答 | 地図上部に必要な質問。推薦ピンなし。0件とは表示しない |
| 適合・根拠／座標／受付時間確認済み | 推薦ピン、条件詳細と公開施設への行き方 |
| 適合だが今は営業時間外 | 適合ピンを維持、閉まっている時刻を併記。現在の営業と持込条件を混同しない |
| 未確認・休止・座標／時間不明 | 推薦ピンと行き方を出さず、確認対象として補助一覧に理由と公式情報を表示 |
| 全件評価済みで適合なし | 「確認できた持込先がありません」と公式情報。条件未回答や通信失敗の0件と区別 |

営業時間がないことを24時間対応へ変換しない。訪問日を変える場合は当日のサービス期間・曜日時刻を再評価。外部地図へ渡すのは公開施設の位置・名称だけ。検索→条件→地図→詳細→戻るで元の品物・回答・タブ・地図位置を保持し、品目変更の地図回答と元の検索回答を別に管理する。

## D4 位置候補の契約

LocationSampleは座標・水平精度・測位の経過時間・要求IDをメモリにだけ持つ。15秒で待ちを終了し、60秒を超える古い測位・精度不明／100m超・負値／非有限値を単一候補の根拠にしない。概略許可でも得られた精度で同じ検査。取消・背景移行・新要求後の古いcallbackは要求IDで捨てる。[Android位置権限](https://developer.android.com/develop/sensors-and-location/location/permissions)を2026-10-10に確認。

GeoPack v1は自治体・releaseId・EPSG:4326・Polygon／MultiPolygon・area IDと対応stream・公開根拠・期間を必須とする。空・自己交差・穴の不正・非有限座標・別CRS・未知ID・版不一致を拒否。streamごとの公表対応範囲と欠落を確認し、全市・全方式を常に覆うとは仮定しない。行政界を収集区域へ代用しない。

精度円に交差・接触する区域はstreamごとに候補として全て残す。同一stream内の境界接触・重なり・穴・隣接自治体・対応範囲外への広がりは単一確定しない。異なるstreamの正当な重なりは曖昧さと扱わない。候補1件でも本人の自宅確認が必要。全て外側でもGPS方式で特定不可という結果であり、住所照合も未対応とは断定しない。精度不足／根拠不足を含め住所選択へ進み、製品のunsupportedと根拠付きnotApplicableを区別する。保存するのは地区IDと必要な条件の意味IDで、座標・数値住所を保存しない。

円とポリゴンの演算には未監査のライブラリや独自の近似を直ちに採用しない。境界・穴・投影誤差・小区域のPoCと依存／ネイティブのライセンス確認を完了するまでGeoPack照合は着手不可。単発OSブリッジはfake応答で独立に検証可能だが、その成功をGPS地区設定成功とは扱わない。

## D5 製品の確定状態と破損復旧

現在のPR #61はfixtureの複数保存をjournalで調整する部分実装。製品では**一つのDeviceState v2**を正とする。確定state（selection：自治体・HomeCollectionProfile全体・releaseId／番号・言語・通知希望・初回案内回答、generation：epochId＋sequence）、pending（世代付きstateのprevious／target・reason・phase・retryReason）を同じ原子的なファイルへ保存する。現在のschema2投影とAndroid通知journalを直接製品へ流用せず、複数binding・部分確定・日跨ぎを持つ派生状態の版を定義する。初回はconfigured=false、自治体／profile／releaseはnull、通知OFF、案内は未回答。未設定を既定の自治体・地区へ変換しない。

pending.previous／targetはselectionだけでなくgenerationも持つ。通常の変更ではpreviousのsequence+1をtargetにし、同じselectionを再保存する場合も世代を区別する。単なる再照合は世代を増やさない。初回の状態をsequence=0とし、新epochは復旧の確認保存時だけ発行する。

| pending.phase | 確定stateの許容値 | 再開時の処理 |
| --- | --- | --- |
| なし | 検証済みの確定state | 同世代の派生状態を再照合 |
| prepared | previous（世代を含め完全一致） | 通知停止を再確認してから処理を進める。保存を進めない取消なら旧stateを再反映 |
| stopped | previous | targetの確定保存または旧state復旧。保存失敗ではprevious維持 |
| committed | target | 新stateの投影と予約を反映 |
| needsRetry | previousまたはtarget。retryReasonがoldReflectionならprevious、newReflectionならtarget | 選ばれた側を再反映し、成功後にpending解消 |

確定stateをtargetへ変える書込みとpending.phase=committedは同じ原子的書込みにする。v2のstopped＋targetの組合せは不正とし、推測で進めない。#61の別ファイル方式でstoppedなのに新selectionが保存済みになるv1とは異なる契約である。準備したbundleやcurrentキャッシュの存在を確定の根拠にしない。

sequenceはepoch内で単調増加し、通常更新でepochを変えない。UI・通知・投影は同じprofile世代・releaseIdと対象binding／calendarを持つ。Androidの配送直前とウィジェット生成時に確定DeviceStateへ照合し、古い世代は配送せず／確認必要へ。ネイティブ側の予約generationはOS内部管理として区別する。整合性検査を読めなければ通知0件ではなく失敗として停止・復旧対象にする。

準備記録→旧通知停止→新selection確定→投影→通知登録→pending解消を直列化。再開時は世代付きstateとphase表に従い、確定stateがpreviousなら旧状態、targetなら新状態を反映する。同じselectionでも世代を省略して比較しない。参照するbundleが欠落／破損なら取得再試行・確認必要にし、旧ファイルの内容を新しいIDに見せない。timeoutで遅いOS呼出が消えるとは扱わず、完了まで後続の保存を進めない。

破損／旧新どちらとも違う状態では次の復旧フローを実装する。

1. 所有通知を停止し、現在のDeviceState・bundleと直前の検証済みバックアップを検査。未知形式は自動修正しない。
2. 検査済みの保存状態がある場合だけ地区・言語・通知希望を確認画面へ示し、「この設定で復旧」／「地区を選び直す」を提供。バックアップなら古い設定であることを明示。バックアップは地区と希望の候補として使い、過去の予定をそのまま再予約しない。訂正済みの旧番号を復帰させず、最新の検証済みbundleと区域・条件を照合し直す。番号や区域の対応を検査できなければ再取得／地区再確認とし、通知を止める。取消は保存を変えず設定へ戻る。
3. 確認後、停止成功を再確認して新epochの復旧意図と確定状態を原子的に保存。投影／予約を再生成する。停止失敗・書込失敗は反映を進めず再試行。
4. 全保存が壊れている場合は地区未設定・通知OFFで確認からやり直す。言語等の検証できた設定だけ引き継ぐ。全データ削除を既定の復旧にしない。

隔離した元ファイルは私有領域に上限付きで保持し、診断送信・公開ログへ含めない。Android AtomicFile等の原子的保存・バックアップ読出しとFlutterからの単一writerをPoCで確認してから導入する。flush＋renameだけで電源断耐久性を保証したとは書かない。

## D6 取得・審査・公開・監視

ジョブ契約ごとにjobKind・contractVersion・requiredSources・requiredStages・開始／検証完了時刻・run ID・outcomeを記録する。最新の実行・進行中・最後の成功を分け、開始しただけのrunを成功履歴にしない。進行中が10分（LLMを含む月次は15分）を超えれば実行停止／遅延として調査する。

| jobKind／段階 | 成功・失敗・停止の契約 |
| --- | --- |
| fetch | 必須ソース全件の許可・本文／構造検証と必要な保管・取得結果保存が成功してvalidatedSuccess。変更なしも成功、部分取得・保存失敗はfailed |
| candidate | 変更ありなら抽出・根拠／期間／schema検査・候補の永続保存とPR集約の全成功がcompleted。変更なしは理由付きnotNeeded。LLM不正／抽出／保存／PR失敗はfailedでfetch成功を取消さず段階失敗を記録 |
| weekly／daily pipeline | fetch=validatedSuccessかつcandidate∈{completed,notNeeded}で揃って初めて成功heartbeat。候補の人の審査待ちは別状態で、未承認の配信はしない |
| monthlyAudit | 許可された全監査対象の点検・結果検査・根拠付きレポート保存までcompleted。予算／送信条件で停止した場合はpausedBudget／pausedPolicyで、実行記録は残すが成功heartbeat・最後の点検成功日時を更新しない |
| publish | 承認された固定commitの検証・配置・公開HTTPS照合までcompleted。候補待ちや変更なしでは公開成功日時を捏造しない |

独立監視はジョブ契約の成功receiptとGitHubの終了status／必須段階を合わせて照合する。意図的停止は異常なしとせずdegradedとして一度知らせ、同じ原因の反復通知を抑える。初めから無効のjobは監視対象外と明記し、有効後の予算停止を監視対象の削除で隠さない。GitHub runの成功だけで外部のmonthlyAuditの完了を推測しない。

取得の結果はattempted／fetchFailed／validatedUnchanged／validatedChangedを区別。sourceごとに試行・取得成功・内容検証・公開の時刻を持つ。必須対象が消えたら対象を減らして成功とせず、部分成功でもそのジョブの成功heartbeatを送らない。

初期の取得は20秒、最大3試行、形式別サイズ上限。CSV2件の現行実装の20秒と揃える。構造不明・空本文・条件付き304で検証済み本文なしは失敗。無効な権利・再配布／LLM送信不可の本文は取得保管／送信を先に止める。権利確認と原文の正しさはスキーマ検査では証明できない。

候補の一意キーはmunicipality＋source差分hash群＋parser版。既存候補PRへ集約し、版の前後・影響日／区域／品目・原文位置・根拠を提示する。全文・精密位置・資格情報を公開PRへ含めない。同じhashでfailed候補を放置せず再試行状態を更新する。対象期間／区域の未知は明示するが、未承認候補を端末へ直接送らない。

審査は採用commit・候補内容hashに対する人の原文照合。一般的な開発許可をその原文確認として流用せず、審査対象と確認日時を記録する。LLMの自己評価やAIレビューを人の承認として扱わない。配信jobはmainの固定commit・承認記録・bundle全体の権利／内容検査に限定し、取得／LLMjobには配信資格情報を渡さない。緊急の告知でも、未承認候補から端末へ直接保留を送らない。人が影響範囲と根拠を確認した保留リリースを先に承認・公開し、該当日／区域だけ確認必要へ切り替える。公開後に実HTTPSのmanifest・bundle・checksumを照合し、最後の公開成功を記録する。誤公開は新しい訂正版と影響範囲を審査し、受信できない端末の予約を取り消せたと扱わない。

週次月曜03:17、日次03:47、月次2日04:17の日本時刻と頻度は維持。月次LLMは異常候補を出す補助で、HTTP・schema・稼働検査を代用しない。モデル／料金・原文送信条件が未確定の間は無効。既存の月3,000円目標／LLM枠1,000円案を基準に、料金確認日・入力／出力上限・再試行を含む予約費用と実績を持つ。全ジョブ共有の予算確保ができなければ並列AIを有効化しない。予算到達はAIだけ停止し、有効なデータとHTTP検査を維持する。

独立監視の第一案は既存アカウントのCloudflare Workerによる毎時のGitHub状態照合。GitHub外で動かし、日次36時間・週次8日・月次35日と最新失敗を評価する。CloudflareからGitHubを読めない場合は不明／異常で、正常通知にしない。GitHub自体が止まった際に届く別経路の通知先と、監視Worker自身の生存heartbeat（毎時、欠落3時間を初期検知値）を受ける外部受信先を登録して試験する。Workerの生存heartbeatはチェック処理と結果の永続記録完了で送るが、監視対象の正常を意味しない。対象が異常でもWorkerが生きている記録を分け、通知送信の失敗は別に失敗として記録する。提供者・通知先・費用・権限が未確定なので未稼働。MacのCodex予定実行へ依存しない。

GitHub scheduleには遅延・欠落や無効化条件があるため、登録だけで成功にしない。[GitHub公式](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)。Cloudflare CronはUTCで登録し、設定反映時間を考慮して初回実行を確認する。[Cloudflare公式](https://developers.cloudflare.com/workers/configuration/cron-triggers/)。どちらも2026-10-10確認。
