# 自治体データの更新・運用設計

状態：頻度と人による確認は合意済み。以下の閾値・時刻・実装方法は提案。ジョブも監視も未作成・未稼働。

## 確認頻度と公開頻度

| 処理 | 合意した頻度 | 変更なしの場合 |
| --- | --- | --- |
| 通常の収集曜日・分別・回収拠点・受付条件 | 週1回 | 正常確認を記録。LLMを呼ばない |
| 臨時のお知らせ・休止情報 | 1日1回 | 正常確認を記録。LLMを呼ばない |
| 変更箇所の抽出 | 差分検知時 | 不要 |
| LLMによる全体点検 | 月1回 | 点検結果を保存。異常なしの通知は原則不要 |
| データ公開 | 検証・人の確認後 | 新版を作らない |

情報取得、候補作成、公開、端末の受信は別の段階である。定期取得しただけでは利用者の予定は更新されない。年末年始や制度の施行日は適用日付きで扱う。

実行時刻は本番構築時にAsia/Tokyo基準で固定し、UTCのスケジューラーへ登録する場合は変換を試験する。通常の週次処理、日次処理、月次処理が同時に重複しないようにする。日次確認でも当日直前の告知を朝の通知に必ず反映できるわけではない。

## 取得から公開まで

1. **ソース登録**：公式URL、種類、取得方法、対象自治体、監視頻度、利用条件の確認状況を登録する。自治体から参照されている民間ページも別ソースとして管理する。
2. **取得**：CSV／API等があれば優先。なければHTML／PDF。適切な間隔・条件付き取得・サイズ上限を設定し、サイト規定を守る。
3. **差分**：共通ヘッダー等を除いて意味のある本文差分を検出。失敗・空本文・構造変化を「変更なし」にしない。
4. **抽出**：決定的なパーサーを優先し、必要な変更だけLLMへ渡す。原文根拠・施行日・例外を必須にする。
5. **機械検証**：スキーマ・ID・期間・区域・条件・出典を確認。既存データとの意味差分を作る。
6. **PR**：変更前後、出典、適用日、影響区域／品目、検証結果、権利確認、復旧方法を付ける。候補段階を本番配信しない。
7. **人の確認**：原文と日程・受付条件を確認してマージする。同じ未解決差分でPRを増殖させず既存PRを更新する。
8. **公開**：不変のデータ版を生成し、検証後manifestを切り替える。版とPRを対応させる。
9. **端末反映**：起動時等に新版を確認して一括更新し、通知・ウィジェットの予定を再生成する。途中で失敗したら有効な旧版を保持する。

LLMにWeb上の指示を実行させない。取得プロセスに本番配信権限を持たせず、抽出候補と承認済みリリースの境界を設ける。初期は意味のあるデータ変更を全件人が確認する。

## 情報が不確かなとき

- 一時的な取得失敗だけで全予定を非表示にしない。確認済み・有効なデータは使い続ける。
- 出典同士が矛盾する、有効期間外、対象日・区域の根拠がない場合は、影響範囲をneeds_confirmationにする。
- 利用者への日程表示は **「収集予定の確認が必要」** と公式リンク。該当する種別を断定する通知は予約しない。
- 未承認の臨時変更は通常予定を確定として扱わないよう、影響範囲を保留にする候補を運用者へ優先提示する。自動判断で取消日を捏造しない。
- 拠点の矛盾・休止・時間不明は「回収条件の確認が必要」「受付時間は要確認」など場所に合う文言にし、推薦から除外する。
- カレンダー生成期間と確認済み期間を分け、確認済み期間を越えて通知を大量予約しない。

端末がオフラインなら、公開された訂正を直ちに受け取れない。初回からこの制約を前提とし、地域・日付・最終確認日・有効範囲を明示する。サーバーのロールバックだけで全端末の予約通知を取り消せるとは考えない。

## 毎回の監視と独立監視

ソース別に「最終試行」「最終取得成功」「最終内容検証」「最終公開」を別々に記録する。変更がないので公開が古い状態と、処理が動いていない状態を区別する。

GitHub Actionsは予定実行が遅れる場合があり、公開リポジトリでは活動が60日ないと定期処理が無効化されることがある。[公式仕様](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

そのため、同じActions内の月次ジョブだけで稼働を監視しない。別事業者のheartbeat／dead-man監視で正常終了報告の欠落を検知する。日次36時間、週次8日、月次35日を初期の遅延検知閾値候補とし、運用時に調整する。これはデータの有効期限ではない。

通常の失敗はIssueへ記録し、同じ原因は集約する。独立監視はGitHub自体の障害でも届く通知経路を1つ確保する。通知先と担当者は有効化前に登録し、試験通知で到達を確認する。異常なしの定例連絡は増やさない。

## 月次LLM点検

最新の公式情報と採用データのサンプル、差分履歴、未承認PR、ソース取得結果を照合する。確認対象は新しい告知の見落とし、ソース移転、抽出漏れ、旧年度の混入、休止解除の誤扱い、出典切れ、処理・監視の稼働状況。

結果は根拠URLと再現手順を持つIssue候補にする。LLMが「正常」と答えても、実行ログ・heartbeat・検証結果を上書きしない。四半期等の頻度は追加合意していないため、月次以外の重い定期監査を勝手に追加しない。

## 障害時の運用手順案

| 異常 | 初動 |
| --- | --- |
| 取得不能／構造変更 | 対象ソースの公開を止め、原文を確認。有限回リトライしIssue化 |
| 間違った日程・受付条件を公開 | 影響区域／日付／品目を特定。安全に使える旧版へ戻すか確認必要状態に修正し、端末更新で通知を再生成 |
| LLM停止／予算到達 | 抽出候補作成を停止。HTTP差分検知と既存の有効データ配信は継続 |
| 定期ジョブ自体の停止 | 独立監視から担当者へ連絡。権限・予定・サービス状態を確認し手動実行で復旧確認 |
| 利用者から誤情報報告 | 住所や写真を公開Issueに求めず、区域ID・品目・出典を基に照合 |

復旧時はデータ版、確認者、影響範囲、再発防止を記録する。運用者が対応できない間は未確認データを推測で公開しない。
