# サブエージェント並列上限の切り分け

2026-10-11。関連[Issue #75](https://github.com/oukiito/gomimap/issues/75)、[PR #76](https://github.com/oukiito/gomimap/pull/76)。利用者から増員と、追加起動が上限エラーになる理由の確認を依頼された。

## 確認できた事実

- 実行中の会話はmulti-agent v2。会話内で案内されている定員は親を含む4枠で、親1＋調査3が稼働している。
- 追加起動は2回とも`collab spawn failed: agent thread limit reached`。利用量上限のエラーとは異なる。追加担当は作成されていない。
- 一般の[公式設定リファレンス](https://learn.chatgpt.com/docs/config-file/config-reference)は`agents.max_concurrent_threads_per_session`を案内する。この値をプロジェクトのローカル設定で6へ変更したが、実行ログの`multi_agent_v2.max_concurrent_threads_per_session`は4のままだった。
- プロジェクトはtrusted。ユーザー設定・選択プロファイル・起動引数に、調べた範囲で別の並列数指定は見つからなかった。
- 実際のアプリ内実行ファイルから、V2用の`features.multi_agent_v2.max_concurrent_threads_per_session`を確認した。同ファイルの一時的な読取専用設定検査で0は最小値エラー、6は受理された。通常CLIとアプリ内実行ファイルを区別して調べた。
- V2用のプロジェクト設定を7（この会話の親1＋子6を意図）へ追加し、実行ファイルによる設定読込は成功した。設定変更後の2026-10-11 02:38:53 JSTの会話ログでも、実効値は4のまま。追加起動の再試行も拒否された。

## 結論と未確定

直接の拒否理由は、現在の会話で4枠が使い切られていること。前回は通常系の設定だけを変更しており、この会話のV2実効値への反映まで確認していなかった。設定ファイルへの保存を増員完了と扱わない。

V2用の値を追加しても、実行中の会話への即時反映は確認できなかった。既存会話の設定保持と、アプリ側の要求単位の上書きのどちらが未反映の原因かは、取得できたログだけでは断定していない。『アプリを再起動すれば必ず6担当になる』とも断定しない。新設定での読み込み直しと、実効値・追加起動の再確認が次の検証になる。

今回、調査担当やアプリを再起動・停止していない。3担当の調査は継続。ローカル設定はGit管理対象外で、認証値・設定全文・他の会話のログを公開物に含めない。CLIでの設定検査はこの会話の実効値を変更した証拠ではない。
